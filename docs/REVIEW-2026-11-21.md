## 2. 机制层面的差异对比（一手 README 核对）

### 2.1 他们的优点 / 我们的缺点

| 维度 | 领先者做法（来源） | 全息记忆现状 | 差距性质 |
|---|---|---|---|
| **记忆形成策略** | mem0 2026-04 新算法：单次 ADD-only 抽取，一次 LLM 调用，无 UPDATE/DELETE；agent 生成的事实为一等公民；实体跨记忆链接（mem0 README） | 完全依赖模型判断后 `memory_write`，无自动抽取；`forget`/supersede 全手工 | **代差**：从「人写库」到「库自己长」 |
| **检索多信号融合** | mem0 语义 + BM25 + 实体匹配三路并行打分；Graphiti 语义 + BM25 + 图遍历混合；mcp-memory-service BM25+向量+recency/frequency/quality 加权 | 词面 + 哈希向量（默认非语义）+ 2 跳图；有 RRF 但无实体 boosting、无 recency/frequency 质量加权 | 中：已有多路骨架，缺信号与重排 |
| **双时态完整度** | Graphiti 双时态（valid time + transaction time）、episodes 溯源到每条派生事实、prescribed/learned ontology（Graphiti README + arXiv 2501.13956） | 有 `valid_from/valid_to/recorded_at` + source，双时态雏形齐全；但无 episode→fact 的强溯源链、无本体 | 中：结构对，语义薄 |
| **渐进披露上下文** | claude-mem：注入 compact index（50-100 token/条），需要时三段式 `search→timeline→get_observations` 拉全文（500-1000 token/条），约为全文 1/10 | 固定 1200 字画像 + top-3 召回，命中即全文注入；无 index/detail 分层 | **高**：Token 效率是同类核心卖点 |
| **记忆质量反馈闭环** | dna-memory：`memory_feedback(useful/misleading)` + `memory value` 度量召回命中/反馈率/重复说明减少；mem0 有 entity linking 与 temporal reasoning | 仅 `solution_report`（success/failed）作用于故障经验，普通 note/fact 无「这条召回到底有没有用」的反馈 | **高**：无法度量记忆价值，只能数条数 |
| **巩固与遗忘** | mcp-memory-service：autonomous consolidation（聚类/压缩/关联发现/受控遗忘）+ insight cards；claude-mem observer 会话末写 summary；dna-memory 八类认知分型 + 验证结晶 | `dream` 只做覆盖度启发式核对、需人工确认；`compact` 只按时间墓碑化转录 | **高**：有治理动作但无「抽象/巩固」 |
| **自动会话捕获** | claude-mem 通过 9 类 hooks 捕获工具调用，第二 agent 实时做笔记 | 依赖宿主 `session/event`；MCP 宿主无事件流，转录不自动增长 | 中：DSH 内有，MCP 内天然缺失 |
| **跨工具生态** | claude-mem 支持 15+ agent；mcp-memory-service 覆盖 LangGraph/CrewAI/AutoGen + 15 IDE + 远程 MCP OAuth | DSH 插件 + MCP + HTTP + CLI，工具面广但绑 DSH 较深 | 中：接口全，生态位窄 |
| **远程/团队** | mcp-memory-service Cloudflare/Milvus 混合后端、OAuth 远程 MCP；caura 多 agent 治理共享 | 纯本地单机、loopback、明确不做鉴权 | 取舍：本地优先是选择，非缺陷 |

### 2.2 他们的缺点 / 我们的优点

| 我们的优势 | 依据 | 竞品对应短板 |
|---|---|---|
| **零依赖、单文件、可审计** | 仅 `node:sqlite` 等内置模块；`omni.db` 单文件备份即复制；星图 Canvas 2D 手写 | mem0 需 LLM+embedding 服务；claude-mem 需 Bun+uv+Chroma+observer 订阅；Graphiti 要自备图库+LLM+embedder，是框架非成品 |
| **默认完全离线、隐私可控** | `OMNI_SCOPE_JUDGE` 默认 `off`，`OMNI_EMBED_URL` 不设则不外发；威胁模型明示边界 | mem0 默认调用 OpenAI；claude-mem observer 有试用期与云端 provider；mcp-memory-service 部分特性依赖外部 LLM |
| **故障经验库独一份** | `problemKey` 指纹 + `solutionStatus` + `evidence` + `reuseCount` + `solution_report` 闭环（ADR-027） | 竞品普遍只有通用记忆，鲜有「症状/失败尝试/有效解法/前提」结构化排障记忆与复用计数 |
| **逻辑删除 + 全审计可回滚** | 墓碑、`valid_to`、`superseded_by`、`dream_rollback`、`restore`、导出含墓碑 | 多数竞品默认检索即隐藏历史；Graphiti 保留时态但无单条回滚工具链 |
| **做梦校验的反幻觉设计** | 覆盖度 + 特征词启发式判定，`apply` 只标记、`commit` 才替代，可一键反替代（ADR-021） | claude-mem observer 直接生成并写入 observation，无「只标记不改写」的中间态 |
| **项目分层 + 归属判断 + 可选模型复核** | `proj:*` 键、措辞规则、`auto/always` 复核（ADR-013/014/015） | dna-memory 无项目隔离语义；basic-memory 按目录但不做归属判断；mem0 用 user_id 而非工作区 |
| **性能与确定性** | 10k 行 p95 2.4ms、1M 行 6ms（有界检索 ADR-020）；零网络往返 | mem0 单次抽取即一次 LLM 调用（p50 0.88s）；claude-mem observer 为异步 agent |
| **许可清晰（虽限制商用）** | 个人使用许可 1.1、署名要求明确 | 部分仓库 license 声明与商业云服务并存；AGPL-3.0（basic-memory）对闭源集成有传染性 |

## 2.5 二次深度评审新增发现（不重复已修项）

独立架构评审另找出一批此前未覆盖、带源码证据的改进点，按主题归纳：

**记忆语义质量**
- **文本分有「地板」**：`index.js:1783/1868` 用 `0.6×max(0.6, textScore, matchRatio)`（facts 基线 0.7），任何被召回条目先拿 0.36/0.42 保底分，文本相关性退化成布尔量；排序实际由 importance/recency 主导，且 facts 系统性压过 notes。→ 改加权连续分，需黄金集校准。
- **有界采样的结构性漏召回**：`SEARCH_WINDOW=20000`、`FTS_SAMPLE=120`、`BIGRAM_SAMPLE=200`、`VECTOR_SAMPLE=5000`（`:1542-1544,2109`）；ADR-025 自承采样外旧记忆不可达。低延迟是用牺牲召回换的。→ notes/facts 全量参与召回，只对 chunks 限窗；按 scope 分桶采样。
- **RRF 只看名次、无重排**：`:2448-2484` 仅 `1/(60+rank)`，命中 12/12 与 2/12 词分数几乎相同，`lexicalScore` 只作诊断。→ top-20 加可插拔 rerank。
- **dream 的替代是 dumping 原文**：`:2007-2012` 把 `evidence.text.slice(0,600)` 当修正结论；中文语义对立（Docker→裸机）检测不到（`:1985-1987` 只认 latin/数字）。→ 替代改为结构化候选，标注「待人工改写」。
- **无巩固/分层摘要**：`memory_compact` 纯按 `ts ASC` 墓碑化（`:3974-3978`），画像 `LIMIT 60` 超预算就 `pop()`（`:2797-2820`）。→ importance/复用度加权 + `memory_condense` 摘要笔记。

**架构**
- **模块级全局单例**：`store`、`profileCache`、`entityCache`、`projectByAgent`、`recallByAgent` 等（`:2397,2846,2220,2873-2953`）阻碍同进程多实例，也是拆 core 的隐藏耦合。→ 收进 `Runtime` 对象显式注入。
- **最干净的切口是 retrieval/store**：纯检索逻辑 `index.js:1458-2495`、存储 `:351-1450`，工具/路由是宿主-facing。→ 先抽 `core/retrieval.mjs` + `core/store.mjs`，`index.js` 保持 re-export；加「导出符号快照」测试防假绿。
- **拆分三重静默风险**：测试直接 import 导出、脚本路径敏感、文档漂移（改造方案:151 已警告）。

**产品实用性**
- **脱离 DSH 后旗舰功能大面积失效（最高优先级）**：`hosts/mcp/README.md:20-24` 自承无自动注入/转录/复核/dream 定时；而 DSH 是小众宿主，主流是 Claude Code/Cursor。→ 宿主无关的转录导入器 + `omni serve` 常驻 + hooks 自动调 `memory_context` + `omni install` 一键接入。
- **缺 `memory_edit`**：改一条笔记要 write+contradicts+forget 三步。→ 加 `memory_amend(id,text,reason)` 保留 revision 连续性。
- **注入不可解释**：注入只有 `[kind#id] text`（`:4663`），三路 score 不展示；超预算时第一个被砍的是最相关的召回（`:4670-4671`）。→ 附 `via=problemKey, verified, 30d` 标签，召回优先保留。

**前沿差距（严格区分）**：已验证且缺——自动事实抽取（mem0）、rerank（RAG 标配）、PPR 图算法（HippoRAG 2）、工具调用捕获（claude-mem，对应 D-12）；推测性——sleeptime 后台 agent（Letta）、社区摘要（Graphiti），建议先自建评测再定。**绝不能丢的独有优势**：只增不改+墓碑审计、双时态事实失效不删、确定性 dream、故障经验闭环、项目分层双向防线。

## 3. 可落地的升级优化（按投入产出比排序）

> 原则：不推翻内核、不改「本地优先 + 零依赖 + 只增不改」的立身之本；优先补**已被同类验证有效**的能力。两路评审（竞品对标 / 架构深评）的建议已在下文合并收敛。

### 大版本最该做的三件事（两路评审收敛结论）

**① 建检索质量闭环：修文本分地板 + 可插拔重排 + MRR 回归门槛**（ROI 最高）
- 依据：两路评审共同首选。`bench/golden.mjs:77-111` 只输出 MRR、无 assert；CI（`ci.yml:16-19`）只跑 check+test；文本分有 `max` 地板压制区分度。
- 做法：`golden.mjs` 加 `assert(mrr >= baseline-0.02)` 并纳入 CI；改 `:1783/1868` 加权连续分；top-20 接可选 rerank（`OMNI_RERANKER`）；notes/facts 全量参与召回解决旧记忆漏召回。
- 收益：**没有门槛，后面任何语义改动都是盲改**——这是其余优化能否量化的前提。成本：低-中。

**② 让核心能力脱离 DSH：宿主无关转录导入 + 自动注入 + 一键接入**（产品价值最大缺口）
- 依据：`hosts/mcp/README.md:20-24` 自承旗舰功能在非 DSH 下失效；DSH 小众，主流 agent 才是用户增长点。
- 做法：实现改造方案规划的 `hosts/ingest`（Claude Code JSONL / Codex 会话 → `insertChunk`）；`memory_context` 做成 hooks 自动调用而非「靠模型自觉」；`omni install --client <name>` 一键配置。
- 收益：把产品从「DSH 插件」变成「通用 AI 记忆内核」。成本：高，但战略必要。

**③ 补「记忆自我改进」主线：反馈闭环 + 自动候选 + 渐进披露**（补代差）
- 依据：竞品普遍有 feedback（dna-memory useful/misleading）、自动抽取（mem0）、渐进披露（claude-mem 1/10 token），本项目三项皆缺。
- 做法：`memory_feedback(useful/misleading)` + 价值面板；离线 opt-in 抽取候选队列（默认 off、需确认、不直接入库）；画像改为 index + `memory_get(ids)` 展开。
- 收益：第一次能度量记忆价值，并把「靠模型自觉写」升级为「有安全网的自动沉淀」。成本：中-高。

> **贯穿性基础设施**：渐进拆 core（retrieval/store 先行）+ 状态收进 Runtime + 导出快照测试。它不是独立一项，而是前三项的「摩擦力放大器」——不拆，新能力都得往 4700 行单体里塞。按「retrieval→store→快照测试→状态收敛」小步走，风险最低，越晚越贵。

> 第③项的三条子能力细化：`memory_feedback` 给 note/fact 加 `lastRecallAt/recallCount/usefulCount/misleadingCount`，命中后由模型回报，打分加反馈分（schema v12）；渐进披露把画像改成「一行摘要+id」，需要时 `memory_get(ids)` 拉全文；自动候选在 `session/event` 后异步生成 1-3 条存 `proposals` 表，需 `memory_accept` 才入库，默认 `OMNI_PROPOSALS=off`。三者都守住「默认不调模型、人把关」的底线。

### 第二梯队（低投入 / 高性价比）

**④ 巩固与衰减（consolidation）**：给 `memory_dream` 增加「近重复聚类 + 摘要合并候选」，参考 mcp-memory-service 的受控遗忘；不自动删除，只产出候选，沿用人工确认。
**⑤ 实体链接与质量分**：把已有 `entities/edges` 用于召回 boosting（mem0 的 entity linking），并给 note 加 `quality` 由反馈与来源可信度计算，进入 RRF 权重。
**⑥ 记忆价值面板**：在 HTTP 面板加一页 `value`——召回命中率、useful/misleading 比、重复写入数、各 scope 活跃度（dna-memory `memory value` 的成熟做法）。
**⑦ Markdown 双向导出/导入**：借鉴 dna-memory/basic-memory「Markdown 为真源」思路，提供 `memory_export --format markdown`，让记忆可用 Obsidian 直接编辑审阅（不改为真源，只做可移植视图）。
**⑧ 测试稳定性 + UI 冒烟**：修 Windows `EBUSY` 清理；给 FR-25/FR-29 加 headless 断言；把 MRR 门槛纳入 CI。

### 第三梯队（结构性，需权衡）

**⑨ 拆 `index.js` 内核**：按改造方案切成 `core/{store,retrieval,facts,dream,backup}` + `ports/{llm,scope,transport}`。4700 行单体是当前最大维护债；但风险高、周期长，建议在上述功能稳定后再动，且以「先抽模块不改行为」为第一步。
**⑩ 跨机远程 MCP + 鉴权**：mcp-memory-service 已做 OAuth 远程 MCP。本项目明确本地优先，若要团队化需引入 token/进程鉴权，与「个人、非商用」许可定位冲突，需先想清楚产品边界。

### 明确不建议照搬

- **不做云端默认/自动上传**：隐私与零依赖是本项目最硬的护城河。
- **不引入重型依赖**（Chroma/Qdrant/Bun/spaCy）：会摧毁单文件可审计的优势。
- **不把自动抽取设为默认开启**：mem0 默认调 LLM，本项目应坚持 `off` 默认、用户显式开启。
- **不追星数对标 118k 的 claude-mem**：其 observer 依赖订阅制，商业模型与本项目许可不兼容。

## 4. 结论

全息记忆在这个赛道里的独特位置不是「功能最多」，而是**唯一一个把排障经验、双时态、可回滚、零依赖与完全本地打包进单文件的个人工具**。头部竞品赢在「记忆自己长出来」和「token 渐进披露」，本项目输在「靠人写」「注入即全文」，以及**旗舰能力在非 DSH 宿主下大面积失效**。

两路独立评审（竞品对标 / 架构深评）收敛出的升级优先级一致：
1. **建检索质量闭环**（MRR 门槛进 CI + 修文本分地板 + 重排）——否则一切语义改动都是盲改；
2. **让能力脱离 DSH**（ingest + 自动注入 + 一键接入）——决定产品还有没有增长空间；
3. **补记忆自我改进主线**（反馈 + 自动候选 + 渐进披露）——补上代差。

并以「渐进拆 core（retrieval/store 先行）」作为贯穿性基础设施。全程守住离线、零依赖、可审计三条底线，**自动抽取/模型调用一律 opt-in**。动手前先把 Windows 测试 `EBUSY` 修掉、把未修的 P1（project 伪层级）补上，让 `245/245` 与「P1 全清」名副其实。
