# ADR-028：多进程并发（多个 AI 客户端共用一份记忆）

- 状态：已采用
- 日期：2026-11-18
- 相关：ADR-001（存储引擎）、ADR-017（HTTP 安全）、ADR-027（故障经验）

## 背景

一个人电脑上同时开多个 AI 客户端是常态：Claude Code、Cursor、Codex、Zed、以及本项目的面板和 CLI。每个客户端都会拉起**自己的一份服务进程**，而这些进程全部指向同一个 `omni.db`。

SQLite 允许多进程打开同一文件，但默认行为是「拿不到写锁立刻报 `SQLITE_BUSY`」。也就是：A 在写，B 一写就失败。原来的实现只有 WAL，没有等待窗口，因此第二个窗口会偶发「database is locked」。

另外三处竞态同样会在多进程下暴露：

1. **去重检查在事务外**——两个进程同时写同一段文字，双方都查不到对方，最后各插一条。
2. **启动即维护**——每个进程打开库都要迁移 schema、重建 FTS/bigram/向量索引。进程一多，启动瞬间就是 N 份全量扫描互相踩。
3. **做梦定时器**——DSH 宿主里 `OMNI_DREAM_INTERVAL_MS` 的定时校验，每个窗口一个，同一条笔记会被重复核对 N 次。

## 决策

1. **等待而不是失败**：`PRAGMA busy_timeout`，默认 5000ms，可用 `OMNI_BUSY_TIMEOUT_MS` 调整（上限 60s）。写锁被占时阻塞等待，不是抛错。
2. **写事务一律 `BEGIN IMMEDIATE`**：进入事务就抢写锁，避免「先读后升级为写」造成的死锁。去重、失效旧事实、建索引都在同一个事务里完成。
3. **去重检查搬进事务**：笔记按 `(scope, text)`、转录按 `(hash, scope)`、事实按 `(subject, relation, scope)` 在拿到写锁后重新查一次；输掉竞态的一方返回 `deduped: true` 而不是插入第二条。
4. **维护租约**：`meta` 表里 `lease:<name>` 存到期时间戳。打开库时的迁移 + 索引回填拿 `lease:open-maintenance`（120s），做梦定时器拿 `lease:dream`（一个间隔）。拿不到就跳过——活由别人干，自己只读。
5. **WAL 上限**：`journal_size_limit = 16MB`，避免多读者把 WAL 拖到无限增长。
6. **不做跨进程缓存同步**：画像缓存 30s 是每进程独立的，另一个窗口刚写的规则最多 30s 后才出现在本窗口注入里。这个延迟被接受，换取零 IPC 复杂度；需要立即一致的场景走 `memory_context` 现查。

## 后果

- 多个客户端可以同时读；写是串行的（SQLite 单写者），每次等待上限 5s。写入本身是毫秒级，正常不会排队到上限。
- 进程被强杀留下的租约会自然过期（120s / 一个间隔），不会永久卡死维护。
- 迁移只会在全机一个进程里跑一次，其余进程最多等 5s 拿租约，拿不到就直接用已迁移的库。
- 仍然不解决「多个进程各自持有旧画像缓存」的问题；文档和 README 里明确写出 30s 窗口，不假装实时。
- 极端写入压力（几十进程持续写）会退化为排队；个人机场景不成立，不做连接池或写队列。
