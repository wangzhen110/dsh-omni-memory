# ADR-022：进程级鉴权与数据库加密的评估结论

- 状态：已评估，不在本插件内实施（记录为明确取舍）
- 日期：2026-11-17
- 关联：ADR-017、THREAT-MODEL、路线第 6 项

## 背景

评审与威胁模型都把两条残余风险列为未解：

1. loopback 不是进程认证：同一用户下的任意进程都能读 `127.0.0.1` 端口，拿到全库；
2. 数据库是明文 SQLite：备份、同步、磁盘取证都能直接读。

路线把"进程级鉴权或 DB 加密"排为第 6 项。这里记录为什么评估后**不在插件层实现**，以及什么条件下应该重新考虑。

## 为什么不做进程级鉴权

插件运行在宿主进程内，HTTP 端口由宿主分配，插件代码与调用它的进程共享同一个 OS 用户。可选方案逐一评估：

| 方案 | 结论 |
|---|---|
| Bearer token（env 注入） | 同用户进程可以读 `~/.dsh` 配置、读环境变量、读进程内存；只能挡住"不知道配置"的脚本，不能挡本机攻击者 |
| 仅允许特定 Origin/Referer | 本机非浏览器进程可以伪造任意头，无法验证调用方身份 |
| 命名管道 + Windows ACL | 需要宿主支持非 HTTP 传输；当前 webServer 只提供 HTTP 路由 |
| 绑定随机端口 + 启动时握手 | 面板同源读取仍要能拿到端口/凭据，最终仍落在同一用户的文件权限上 |
| OS 用户隔离（独立服务账户） | 改变部署模型；插件无法自我提权/创建服务 |

**结论：在"宿主进程 + 同一用户 + loopback HTTP"这个模型里，插件层做不出真正的进程认证。** 能挡的只是"不知道插件存在"的偶然访问，而这类访问已经被 loopback 与 CSRF 挡住了；再加 token 只会增加配置负担和面板失联风险，不改变威胁面。真正的隔离需要 OS 账户或宿主提供的进程内 RPC 通道。

## 为什么不做数据库加密

| 方案 | 结论 |
|---|---|
| SQLCipher | `node:sqlite` 不带加密扩展，需自定义原生构建，分发与平台风险高 |
| 应用层加密字段 | 检索依赖 FTS/向量/图对明文建索引；逐字段加密会让检索退化为全解密扫描，违背 1M 行延迟目标 |
| 密钥管理 | 密钥最终要落在同一用户的文件里；对本机攻击者等价于明文，只是提高了门槛 |
| 整盘加密（BitLocker） | 属于用户环境责任，确实有效；应在 README 里建议而不是由插件实现 |

**结论：插件内加密收益低、复杂度高、会破坏检索性能。** 正确做法是把"数据库明文"写进威胁模型与 README，建议用户开启系统级磁盘加密。

## 实际采取的措施

1. **写操作 CSRF 与同源校验**（ADR-017）：挡住浏览器跨站删除/替代。
2. **读路径 loopback + scope 隔离**：挡住网络来源与跨项目读取。
3. **权限提示**：README 与 THREAT-MODEL 明写"库是明文，loopback 不是进程认证"。
4. **导出文件**：与库同一边界，明文 JSON，不做额外加密（避免制造"加密了所以安全"的错觉）。
5. **建议用户开启 BitLocker / FileVault / 全盘加密**，并限制 `%USERPROFILE%\.dsh` 的目录权限。

## 重新评估的条件

- 宿主提供进程内 RPC 或命名管道传输；
- 出现"多用户共用一台机器"的部署场景；
- `node:sqlite` 或其替代支持透明加密且不牺牲 FTS/向量索引；
- 插件从"本机工具"变成"常驻服务"。

## 残余风险（继续记录）

- 同用户进程可读全库；
- 明文库可被备份/同步工具复制；
- 导出 JSON 可被复制扩散，无法远程撤销。
